# Архитектура Linqor

## 1. Назначение

Linqor — приложение для обмена данными между двумя устройствами через отдельную сессию, инициируемую QR-кодом. Клиентские платформы: браузер на Windows 10/11 и Android.

## 2. Клиентские приложения

### Web — `apps/web`
React + TypeScript + Vite. Отвечает за регистрацию и вход, создание/подтверждение подключения, состояние сессии, сообщения, файлы, историю, настройки и управление устройствами.

### Android — `apps/android`
React Native + Expo + TypeScript. Реализует те же пользовательские сценарии с платформенными адаптерами камеры, файловой системы, буфера обмена и защищённого локального хранилища.

### Общие пакеты — `packages/*`
- `domain`: доменные модели устройств, сессий и передач.
- `protocol`: типизированные контракты сообщений и pairing.
- `validation`: проверка входных данных.
- `crypto`: платформонезависимые криптографические интерфейсы. Реальные алгоритмы не должны добавляться до утверждения криптографической спецификации и модели угроз.

Общие пакеты не должны импортировать React, Expo, DOM или платформенные API. Доступ к камере, файловой системе и защищённому хранилищу реализуется через адаптеры конкретного клиента.

## 3. Серверный слой и данные

### `services/edge`
Предполагаемая зона ответственности: проверка полномочий, создание и завершение сессий, координация устройств, выдача короткоживущих данных для установления соединения, контроль доступа к содержимому и ограничения времени хранения.

### Supabase
Выбран как направление для аутентификации, базы данных и пользовательских данных. Схема таблиц, RLS и миграции должны быть спроектированы отдельно. Клиенты используют только публичный anon/publishable key; service role key не может попадать в приложение.

### Cloudflare
Выбрана как инфраструктурная платформа для edge-логики, координации и/или хранения файлов. Конкретные продукты и распределение ответственности ещё требуют фиксации.

## 4. Жизненный цикл подключения

1. Пользователь входит в Linqor на первом устройстве.
2. Приложение создаёт короткоживущий запрос и показывает QR-код.
3. Второе устройство сканирует QR-код и проходит проверку.
4. Первое устройство подтверждает запрос.
5. Сервер создаёт новую сессию и связывает в ней два устройства.
6. Устройства обмениваются данными в рамках сессии.
7. Пользователь просматривает содержимое, копирует текст или скачивает файлы.
8. При завершении или истечении срока действия сессии временные данные обрабатываются по правилам хранения.

Новое QR-подключение всегда создаёт новую сессию. QR payload не должен содержать пароль, мастер-ключ или содержимое сессии — только ограниченный по времени токен/идентификатор запроса.

## 5. Аутентификация и ключи

Supabase Auth — выбранное направление для учётных записей. Конкретный набор способов входа и UX регистрации должен быть закреплён отдельным решением.

Для E2EE-архивов пароль расшифровки совпадает с паролем входа в Linqor. При первом входе клиент получает возможность расшифровать мастер-ключ и сохраняет его в защищённом локальном хранилище устройства. На уже настроенном устройстве мастер-ключ восстанавливается из защищённого хранилища без повторного ввода пароля; на новом устройстве пароль потребуется снова.

Это требование не означает, что пароль можно хранить в открытом виде или передавать серверу для расшифровки. Сервер не должен получать мастер-ключ или plaintext содержимого. Реализация KDF, wrapping, ротации, восстановления и защиты от перебора должна быть описана в криптографической спецификации до реализации.

## 6. Сессии и хранение

Следует различать:
- активную сессию — текущее взаимодействие устройств;
- сохранённое содержимое — доступная пользователю история и материалы;
- учётную запись — постоянные данные пользователя;
- локальный ключевой материал — секреты, хранящиеся только в защищённом хранилище устройства.

Для сохранённого содержимого выбран ограниченный срок хранения; рабочий ориентир — до 7 суток. Точка отсчёта, исключения и механизм удаления требуют отдельной спецификации. Удаление должно охватывать связанные метаданные и файлы.

## 7. Безопасность

- Регистрация и аутентификация обязательны.
- Подключение подтверждается на уже авторизованном устройстве.
- QR-токены непредсказуемы, краткоживущие и одноразовые либо строго ограниченные.
- Сервер проверяет права доступа к каждой сессии и каждому файлу.
- Секреты и пользовательские файлы не попадают в Git и логи.
- Ограничиваются размер и тип передаваемых файлов.
- Имена файлов и пользовательский ввод обрабатываются безопасно.
- Временные данные удаляются по установленным правилам.
- E2EE нельзя считать реализованным до реализации и тестирования утверждённого протокола.

## 8. Инструменты разработки

- pnpm workspaces + Turborepo — монорепозиторий.
- TypeScript — общий язык клиентских приложений и пакетов.
- GitHub Actions — автоматические проверки.
- Vitest/Playwright — целевые инструменты тестирования; тестовые сценарии добавляются вместе с функциональностью.

## 9. Открытые архитектурные вопросы

- Конкретные продукты Cloudflare и схема API.
- Прямой P2P, relay или гибридная передача.
- Транспорт для сообщений и файлов.
- Полная криптографическая спецификация и модель угроз.
- Точная схема БД и политики RLS.
- Лимиты файлов, пропускной способности и количества устройств.
- Точная семантика удаления данных.
- Поведение при закрытии вкладки и работе Android в фоне.
